# 第一性原理分析

## 目的

用户带着一个要设计的东西或一个待审的判断来。你要交付的是**一份过程可见的推导**：需求怎么拆的、每条约束怎么被审的、结论怎么从幸存约束拼出来的——不是只交一个判决。

先分流，两种意图走同一套硬序，只在第 3 步分岔：

- **设计型**（重构 X / 从头设计 X）→ 第 3 步产出重建方案；
- **审判型**（真的需要 X 吗 / 凭什么合理）→ 第 3 步坍缩为「维持 / 推翻 + 凭什么」。

## 硬序

防锚定的关键不在输出顺序，在**现状以什么身份出场**：它只能在第 2 步的表里当被告，不得当主角。

1. **要什么**：把用户的目标拆成子需求表（子需求 + 验收口径）。每行子需求只描述**要达成的效果**，不描述现在由谁/什么实现——本节不得出现任何现有方案、repo、组件的名字（审判型的待审对象可以在开头点名，但子需求行同样只写效果）。对目标本身问一次、只问一次：它是为了什么？上一层若能用别的方式达成，说出来。

2. **审约束**：把所有「不能改」的前提逐条过堂，每条回答三件事：谁定的 / 哪来的；**使它失效的具体事件**——它发生了这条就不成立，说不出来就判为习惯、划掉；判定（硬约束 / 习惯 / 未验假设）。现状的每个设计决定都是本表的一行被告。**禁止**为现状单开章节、量化「现状与目标的距离」、做考古式逐行归因——了解现状的调研随便做，但产出只能折叠进这张表。

3. **重建**：只从第 1 步的子需求 + 第 2 步幸存的硬约束往上拼，写出推导过程——为什么这个形状是被约束逼出来的，而不是从候选里挑出来的。拼完之后才允许回头对照现状，且只回答一个问题：**怎么迁过去**；不得用现状修正结论。审判型在此坍缩为裁决。

4. **押注**：结论押在哪些假设上，逐条写成条件表「我假设 X；若实为 Y，结论变成 Z」。停在哪也分开写清：哪些是推不动了，哪些是你不知道下面是什么。

## 输出契约

- **一次成型**：调研过程随便用工具，但**判断只成文一次**——一条完整消息，或用户指定的一份文档。中途推翻了自己就改稿重写，不发更正流水账，不把半成品判断流式甩给用户。
- 固定骨架：`## 1. 要什么`（子需求表）→ `## 2. 审约束`（审判表）→ `## 3. 重建` → `## 4. 押注`（条件表）→ 结尾 **Key Insight** 一句话：哪个默认假设在绑架判断。
- 每个具体数字后面跟出处：URL / 文件路径 / commit / 合同条款 /「用户答的」；给不出的原地写「我猜的」，不许省略这三个字。
- 说人话：表格列名和正文用读者无需上下文就能懂的话；内部代号、内部行话首次出现必须带一句解释。
- **过程纪律不进交付物**：本 skill 对你的过程要求（问一次、先写哪节、现状何时出场等）只约束你怎么做；交付的文档里不得出现过程自述——「问一次」「拼完才看现状」「说人话」「被告」这类 skill 内部用语，以及任何面向 skill 的元标注。标题、列名、括号注记一律用读者的语言写。

## 交互纪律

- **不许以问代答**。撞上你无权知道的事（这条是谁定的、这个数是测的还是拍的、这个目标是谁的）：能假设的就假设，写进押注表，别问。答案不同结论就不同、且连假设都给不出的，才停下来问——**一次只问一个**，拿到答案接着往下推完。一次分析超过 3 问，说明前两步没拆够，回去拆。
- 答案不同但结论相同的，永远不要问。
- 问完必须推到结论；不得把问题清单当成分析结果交出去。

## 交付前自检

每条都可证伪，违约就改完再交：

1. 第 1 节的子需求全部是效果描述，没有任何现有方案 / repo / 组件的名字；
2. 第 2 节表每行的「使它失效的具体事件」非空，或该行已判为习惯并划掉；
3. 第 3 节用到的每条约束都能在第 2 节找到幸存行；
4. 全文没有「现状距离」量化章节，没有对现状的逐行考古；
5. 每个具体数字带出处或「我猜的」；
6. 判断成文只交了一次，对话里没有散落被推翻的中间判断;
7. 结尾有且只有一句 Key Insight；
8. 文档里没有 skill 过程自述或元标注（「问一次」「拼完才看现状」等字样出现即违约）。
