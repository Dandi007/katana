# Cross-Consistency Cold-Read Prompt Template

> 多文档交叉一致性 review 的 subagent prompt 模板。
> 当一组文档被当作一对 / 一套交付物（比如"需求 + 设计"、"spec + plan"、"主文档 + 附录"）交付时，除了单独冷读每份文档，还要派一个 subagent 同时打开它们，检查一致性。
>
> 使用方法：把模板里 `<ANGLE_BRACKETS>` 占位符替换成实际内容，作为 `task(subagent_type="oracle", prompt="...", run_in_background=true, load_skills=[])` 的 prompt。

---

```text
ROLE: 你是一个**文档一致性审查员**。你会打开这组文档，检查它们互相之间的一致性，以及**作为一组交付物**整体的可读性。

你只能读这 <N> 份文件：
1. `<文件1 绝对路径>`
2. `<文件2 绝对路径>`
...

**硬约束**：不能打开 <列出相邻的 work folder / repo 里所有其他文件的绝对路径>，不能打开源代码仓库。

GOAL: 假设读者**按顺序先读 <文件A> 再读 <文件B>**（或反过来），检查这组文档作为一套交付物的一致性。

REVIEW 问题清单：

1. **术语表一致性**：如果每份文档都有术语节，比较定义：
   - 是否有术语在一份里定义、另一份里没定义但出现
   - 同一术语在不同份里的定义是否一致
   - 有没有冗余（多份重复定义了整段）；是否必要

2. **核心概念 / 实体 / schema 交叉一致性**：
   - 一份文档列的实体（workflow / endpoint / 字段 / 组件）是否在另一份里都有对应的技术实现 / 引用？
   - 实体命名是否一致？有没有漏、多、命名不匹配？
   - 一份定义、另一份只引用时，引用是否准确？

3. **阶段 / 分期 / 优先级一致性**：如果文档都提到 Phase A/B/C 或 P0/P1/P2，定义是否一致？scope 是否冲突？

4. **设计原则 / 约束一致性**：比如某个设计哲学在两份里都讲，两处说法是否吻合？

5. **非目标 / 不做清单一致性**：一份的"非目标"和另一份的"风险 / 开放问题"之间，有没有矛盾？（比如一份说"不做 X"，另一份在某个 Phase 里包含了 X）

6. **References 交叉一致性**：多份文档引用的外部文件是否一致？一份引了另一份没引的情况，是不是合理？

7. **阅读顺序与循环依赖**：多份文档互相引用时，是否形成**循环依赖**（A 假设你读过 B，B 又假设你读过 A）？有没有明确推荐阅读顺序？

8. **作为一组交付物的完整性**：把所有文档加起来，读者能否回答下面这些问题？
   - 要做什么？
   - 给谁用？
   - 用什么技术栈？
   - 怎么部署？（如果适用）
   - 分几期做？（如果适用）
   - 有哪些风险？
   - 有哪些还没决定的问题？
   
   如果还有问题答不上来，这是所有文档一起漏了，还是哪份文档该补？

**输出格式**：Markdown。分 8 节对应上面 8 个问题。问题按严重程度排序，每条要精确到 **文件名 + 章节 / 行号**。最后给一个"总体评价"——作为一组交付物，这套文档能直接发给**没看过 work folder 其他文件的** <目标读者角色> 吗？还是必须补一份 README / START_HERE 才能发？
```

---

## 调用样例

```python
task(
    subagent_type="oracle",
    load_skills=[],
    run_in_background=True,
    description="Cross-check consistency between needs and design docs",
    prompt="""
ROLE: 你是一个**文档一致性审查员**...

你只能读这 2 份文件：
1. `/path/to/frontend-ui-needs.md`
2. `/path/to/electron-design-analysis.md`

**硬约束**：不能打开 ...

GOAL: ...

REVIEW 问题清单：
1. ...
"""
)
```

## 多份文档派发策略

假设需要 review `N` 份文档：

| 文档数 | 派 subagent 数 | 分工 |
|---|---|---|
| 1 | 1 | 单文档冷读 |
| 2 | 3 | 2 个单文档冷读（每份 1 个，互不交叉）+ 1 个交叉一致性 |
| 3 | 4 | 3 个单文档冷读 + 1 个交叉一致性（打开全部 3 份）|
| 4+ | 至少 N+1 | N 个单文档冷读 + 1-2 个交叉一致性（可按关系成对或整组）|

**全部 subagent 必须在同一个响应里派出**，`run_in_background=true`，避免串行浪费时间。

## 何时需要交叉一致性 review？

**需要**：
- 两份/多份文档被当作一套交付物（需求+设计、spec+plan、主文档+附录）
- 多份文档互相引用、共用术语、共用 schema
- 合作方会先看一份再看另一份

**不需要**：
- 单一文档
- 多份文档只是放在同一目录但内容互不相关
- 其中一份只作为 reference，不要求读者真的读完它

## 交叉一致性 review 的常见问题类型

| 类型 | 例子 |
|---|---|
| **命名漂移** | A 里叫 `POST /api/v1/tasks/start`，B 里叫 `POST /tasks/start` |
| **Schema 漂移** | A 定义 `{ok, request_id, error}`，B 定义 `{success, code, msg}` |
| **Phase scope 冲突** | A 说"Phase C 不做 X"，B 的 Phase C 表格里包含 X |
| **术语漂移** | A 把 `task` 定义为"一次采集"，B 把 `task` 定义为"一次推理循环" |
| **单向引用断裂** | A 说"见 B §3.1"，但 B 里根本没 §3.1（或 §3.1 不是 A 暗示的内容） |
| **阅读顺序不明** | A 假设读者读过 B，B 假设读者读过 A |
| **冗余导致维护漂移** | 同一段内容在 A 和 B 里各写一份，未来容易只改一份忘改另一份 |

## 禁忌

- **不要**让一个 subagent 同时做单文档冷读 + 交叉一致性——应该分开派
- **不要**在交叉一致性 prompt 里写"你之前已经读过单文档 review 了"——这会引入锚定
- **不要**让交叉一致性 subagent 读被 review 的文档以外的任何文件
- **不要**跳过"总体评价"——这是最值钱的单句输出（"能不能直接发 / 还是必须补 README"）
